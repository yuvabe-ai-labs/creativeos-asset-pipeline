# Model catalog 1b-i — the server reads image and video models from the catalog Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every server path that runs an image or video model (the image, composite, video and video-edit routes, the avatar routes, the billed image run, the upstream preview and the three Trigger tasks) takes the model's data from the `ai_models` row and only its `generate` code from an adapter map, and refuses a model the catalog says may not run.

**Architecture:** A model's data (label, params and the Zod schema built from them, rules, image inputs, limits, `supportsMask`, `maxReferenceImages`) comes from its catalog row through `to-spec.ts`; capabilities are now Zod-typed per kind (D562). The hand-copied server registries are replaced, for every caller, by two adapter maps, `imageAdapters` and `videoAdapters`, keyed by a per-model `adapter_key` and handed the row's `provider_model_id` (D561). Migration 0084 sets those two columns and re-syncs the rows from the registries. One helper, `runnableModel`, decides whether a model may run (D563). Trigger tasks look the row up in the catalog at run time and skip the status check the route already made (D564).

**Tech Stack:** Next.js route handlers, Supabase Postgres, Zod 4, Vitest 4, Trigger.dev v3.

**Follows:** `docs/superpowers/plans/2026-11-21-model-catalog-1a-foundation.md` (the tables, `getAiCatalog`, `parseAiModelRow`, `toImageClientSpec`, `toVideoClientSpec`). Spec: `docs/superpowers/specs/2026-11-21-model-catalog-design.md` ("A run", statuses, `adapter_key`, edge cases).

## Global Constraints

- Migration **0084** (`supabase/migrations/0084_ai_models_adapters.sql`). Decisions **D561–D564**. Every migration gets its entry in `docs/auth-production-migration.md` (CRLF line endings) in the same commit, with verify SQL.
- **Deploy order:** 0084 is applied (staging, then production) **before** this code runs on Vercel or Trigger.dev. Without it every row still has a family key (`image:openai`, `video:kling`, …) and no `provider_model_id`, no adapter resolves, and every image and video run is refused.
- 0077 is frozen history (Task 2 pins it). 0084 is generated by `src/lib/ai-models/adapter-sync.ts` with a drift test, the same pattern as 0077. Once 0084 is applied anywhere, a registry change goes in a new migration, not a rewrite of 0084. Plan 1b-iii deletes the registries and freezes 0084.
- 0084 never writes `status`, `replaced_by` or `sort_order`: those belong to the super admin.
- On the server, a model's data comes only from the catalog; only `generate` comes from code. Every key in an adapter map is registered exactly once. Retired models (Veo, `gpt-image-1`) get no adapter.
- Refusal copy, exactly: retired → `"This model was retired. Pick another."`; draft, hidden on another node, unknown, or no adapter → `"This model isn't available. Pick another."`. Never name the id, a vendor or an internal error in either. HTTP codes stay as today: a refused model is a **400** on every route.
- Each route loads the catalog once per request with `getAiCatalog()` (60 s cache), in `Promise.all` with its other independent reads. Nothing per item. Auth stays resolved once (`withNode` / `withClient` already do it).
- Text and service models are out of scope (see "Not in this plan"). No browser component changes; shadcn-only controls and plain user-facing copy still apply to anything touched.
- No AI attribution in commits (no `Co-Authored-By`, no "Generated with" line). Stage files by explicit path, never `git add -A` or `git add .`.
- No database connections by the implementer. Migrations are applied by hand in the Supabase SQL editor by the user.
- `npx tsc --noEmit -p tsconfig.json`: the only known errors are under `.next/` from the showcase pages. Any other error is new and must be fixed.
- Known flakes: a full `npx vitest run` has about 11 API route timeouts that pass alone. Verify per directory; re-run a failing route file alone before treating it as broken.

```ts
// D561 — the ai_models rows the migrations leave behind (0077, 0079 and 0082 insert, 0084
// updates), with the seeded prices, for tests anywhere in the app. Not imported by app code.
import { existsSync, readFileSync } from "node:fs";
import { resolve } from "node:path";
import { SEED_JSON_TAG } from "./seed";
import { parseAiModelRow } from "./schema";
import { seededCatalog } from "./test-prices";
import type { AiCatalog, AiModel, AiModelKind } from "./types";

const INSERTS = ["0077_ai_models_seed.sql", "0079_ai_service_models.sql", "0082_ai_text_models.sql"];
const UPDATES = ["0084_ai_models_adapters.sql"];

type SeedJsonRow = Record<string, unknown> & { id: string };

function rowsOf(name: string): SeedJsonRow[] {
  const file = resolve(process.cwd(), "supabase/migrations", name);
  if (!existsSync(file)) return [];
  const sql = readFileSync(file, "utf8");
  return JSON.parse(sql.slice(sql.indexOf(SEED_JSON_TAG) + SEED_JSON_TAG.length, sql.lastIndexOf(SEED_JSON_TAG)));
}

let cached: AiCatalog | null = null;

export function seededModelCatalog(): AiCatalog {
  if (cached) return cached;
  const updates = new Map(UPDATES.flatMap(rowsOf).map((r) => [r.id, r]));
  const models = INSERTS.flatMap(rowsOf).map((row) => {
    // As the database returns it: the columns a seed leaves to defaults, then 0084's update.
    const stored = { description: null, provider_model_id: null, updated_at: "2026-11-23T00:00:00Z", ...row, ...updates.get(row.id) };
    const model = parseAiModelRow(stored);
    if (!model) throw new Error(`seeded row ${row.id} fails the catalog's check`);
    return model;
  });
  cached = { models, prices: seededCatalog().prices };
  return cached;
}

/** The catalog with one model changed (status, capabilities, …). The original is untouched. */
export function withModel(catalog: AiCatalog, id: string, patch: Partial<AiModel>): AiCatalog {
  return { ...catalog, models: catalog.models.map((m) => (m.id === id ? { ...m, ...patch } : m)) };
}

/** An adapter map with `adapter` under every non-retired seeded row of this kind. */
export function stubAdapters<A>(kind: AiModelKind, adapter: A): Record<string, A> {
  return Object.fromEntries(
    seededModelCatalog()
      .models.filter((m) => m.kind === kind && m.status !== "retired")
      .map((m) => [m.adapterKey, adapter]),
  );
}
```

```ts
function vendorName(row: { id: string; kind: string; provider: string }): string {
  const known = VENDOR_NAMES[row.id];
  if (known) return known;
  if (row.kind === "image" && (row.provider === "openai" || row.provider === "gemini")) return nameOf(row.id);
  throw new Error(`No provider model name for ${row.id}: add it to VENDOR_NAMES`);
}
```

```ts
// D563 — whether a model may run, decided in one place for every route, the billed image run and
// the Trigger tasks. Pure and client-safe: the adapter maps are passed in.
//   live    — runs
//   hidden  — runs only on the node that already uses it
//   retired — refused, with the replacement the catalog names
//   draft, unknown, no adapter in this build — refused
import type { AiCatalog, AiModel, AiModelKind } from "./types";

export const MODEL_RETIRED_MESSAGE = "This model was retired. Pick another.";
export const MODEL_UNAVAILABLE_MESSAGE = "This model isn't available. Pick another.";

export type ModelRefusal = {
  ok: false;
  reason: "retired" | "unavailable";
  message: string;
  /** The model offered instead of a retired one. */
  replacedBy: string | null;
};

export type RunOptions = {
  /** The model the node already uses (its stored data.modelId): a hidden model keeps running there. */
  existingNodeModelId?: string | null;
  /** False in a Trigger task: the route checked the status when it reserved the run (D564). */
  checkStatus?: boolean;
};

/** A task's model lookup failed. Final: no retry finds a row or an adapter that isn't there. */
export class ModelUnavailableError extends Error {}

const unavailable = (): ModelRefusal => ({
  ok: false, reason: "unavailable", message: MODEL_UNAVAILABLE_MESSAGE, replacedBy: null,
});

export function runnableModel<A>(
  catalog: AiCatalog,
  modelId: string,
  opts: RunOptions & { kind: AiModelKind; adapters: Readonly<Record<string, A>> },
): { ok: true; model: AiModel & { providerModelId: string }; adapter: A } | ModelRefusal {
  const model = catalog.models.find((m) => m.id === modelId && m.kind === opts.kind);
  // The id came from the request: never echo it.
  if (!model) return unavailable();
  if (opts.checkStatus !== false) {
    if (model.status === "retired") {
      return { ok: false, reason: "retired", message: MODEL_RETIRED_MESSAGE, replacedBy: model.replacedBy };
    }
    if (model.status === "draft") return unavailable();
    if (model.status === "hidden" && opts.existingNodeModelId !== modelId) return unavailable();
  }
  const adapter = Object.prototype.hasOwnProperty.call(opts.adapters, model.adapterKey)
    ? opts.adapters[model.adapterKey]
    : undefined;
  if (adapter === undefined || !model.providerModelId) {
    // A row this build can't run: migration 0084 not applied, or a row ahead of the code.
    console.error("[ai-models] model can't run in this build", {
      modelId, adapterKey: model.adapterKey, providerModelId: model.providerModelId,
    });
    return unavailable();
  }
  return { ok: true, model: { ...model, providerModelId: model.providerModelId }, adapter };
}

/** The model a node's preview reads: its stored model while it may still run there, else the fallback. */
export function usableModelId(
  catalog: AiCatalog,
  modelId: string,
  opts: { kind: AiModelKind; fallbackId: string },
): string {
  const model = catalog.models.find((m) => m.id === modelId && m.kind === opts.kind);
  return model && (model.status === "live" || model.status === "hidden") ? modelId : opts.fallbackId;
}

/** A node's stored model id (`data.modelId`), or null. */
export function nodeModelId(data: unknown): string | null {
  if (!data || typeof data !== "object") return null;
  const id = (data as { modelId?: unknown }).modelId;
  return typeof id === "string" ? id : null;
}
```

```ts
import "server-only";
import { getAiCatalog } from "@/lib/ai-models/catalog";
import { runnableModel, ModelUnavailableError, type ModelRefusal, type RunOptions } from "@/lib/ai-models/runnable";
import { toImageClientSpec } from "@/lib/ai-models/to-spec";

import type { ClientModelSpec, ImageGenInput, ImageGenResult } from "./types";

// D561, D563 — an image model as the server runs it: its data from the catalog row, its generate
// from the adapter map.
export type ImageRun = {
  ok: true;
  spec: ClientModelSpec;
  generate: (input: ImageGenInput) => Promise<ImageGenResult>;
};

export function imageRun(catalog: AiCatalog, modelId: string, opts: RunOptions = {}): ImageRun | ModelRefusal {
  const found = runnableModel(catalog, modelId, { ...opts, kind: "image", adapters: imageAdapters });
  if (!found.ok) return found;
  const spec = toImageClientSpec(found.model);
  const ctx = { spec, providerModelId: found.model.providerModelId };
  return { ok: true, spec, generate: (input) => found.adapter(input, ctx) };
}

  if (!run.ok) throw new ModelUnavailableError(run.message);
  return run.generate;
```

### Task 7: Trigger tasks dispatch through the adapter maps (D564)

**Files:**
- Modify: `trigger/image-generate.ts`, `trigger/video-generate.ts`, `trigger/avatar-voice-preview.ts`

**Interfaces:**
- Consumes: `imageGenerateForTask`, `videoGenerateForTask`, `ModelUnavailableError` (Task 4).

**Why the catalog at run time, not the payload.** The tasks look the row up by `modelId`, which every payload already carries (the voice preview derives it from `VOICE_PREVIEW_ENGINE`). Putting the spec or adapter key in the payload would add a contract between two builds that deploy separately: a run queued by the previous Vercel build has no such field, and the voice preview payload has no model at all. The lookup costs one cached read per worker per minute. The status is not checked again, because the route checked it when it reserved the run and a reserved run keeps what it reserved with (spec, edge cases). The task tests are `image-run.test.ts` and `video-run.test.ts` (Task 4): the tasks hold no logic of their own beyond the call.

```markdown
### D561 — The server takes a model's data from the catalog and only its code from an adapter *(recorded 2026-11-23; refines D552)*

**Decision.** On the server, an image or video model's label, params and the schema built from them, rules, image inputs, limits, `supportsMask` and `maxReferenceImages` come from its `ai_models` row through `to-spec.ts`. Only `generate` comes from code: two adapter maps, `imageAdapters` and `videoAdapters`, keyed by the row's `adapter_key`, each key registered once. `adapter_key` names one model's adapter, `<kind>:<our id after the provider prefix>` (`image:gpt-image-2`, `video:gemini-omni-1.2-flash`); one function may sit under several keys. The adapter is handed the catalog spec and the row's `provider_model_id`, so the vendor's model name (Seedance's and Seedream's dated names, Omni's API model, Kling's endpoint model) comes from the row and a vendor bump needs no deploy. Retired models (Veo, `gpt-image-1`) have no adapter. Migration 0084 sets both columns and re-syncs label, params, rules and capabilities from the registries, never status, replacement or order; it is generated by a builder with a drift test, and 0077 is pinned as frozen history. A test proves every live model's catalog spec equals what the server registries ran with (Kling's rules were already the client map's). 0084 is applied before this code deploys.

**Why.** The server registries were hand copies of the client specs plus `generate`; the catalog cannot drive the server while a second copy decides what runs.

**Rejected.** A family key (`video:kling`) dispatching on the model id inside the adapter: the spec says an unregistered key cannot be set live, which needs one key per model. Rewriting the adapters to be generic over vendors: not needed to read the vendor name from the row.

**Originated →** [2026-11-23-model-catalog-1b-server.md](../plans/2026-11-23-model-catalog-1b-server.md).

### D562 — Image and video capabilities are typed *(recorded 2026-11-23; refines D552)*

**Decision.** `capabilities` is checked by kind when the catalog loads: an image row against the image limits (`maxReferenceImages`, `maxReferenceSizeBytes`, the optional edge, ratio, multiple, total-size and mask fields), a video row against `maxDurationSeconds` and `imageInputs`. A row that fails is logged and left out of the catalog. A key the build doesn't know is dropped, not refused. Other kinds keep an untyped object (they hold none today). Every seeded row passes, and tests assert it.

**Why.** The route reads limits off the row now; an untyped value would reach the request unchecked.

**Rejected.** Strict objects that refuse an unknown key: a row written by a newer build would vanish from an older one mid-deploy.

**Originated →** [2026-11-23-model-catalog-1b-server.md](../plans/2026-11-23-model-catalog-1b-server.md).

### D563 — One check decides whether a model runs *(recorded 2026-11-23; refines D552, replaces D461/D467's deprecated refusals on the server)*

**Decision.** `runnableModel` (`src/lib/ai-models/runnable.ts`) is used by the image, composite, video and video-edit routes, both avatar image routes and the billed image run: `live` runs; `hidden` runs only when the node already uses that model (its stored `data.modelId`), so an avatar or a script panel, which have no node, cannot start one; `retired` is refused with "This model was retired. Pick another." and its `replaced_by`; `draft`, an unknown id, a wrong kind, and a row whose adapter or provider model name this build lacks are refused with "This model isn't available. Pick another.", never naming the id. The routes keep answering 400. Each route reads the catalog once (`getAiCatalog`, cached), beside its other independent reads. The Upstream preview falls back to the default model for a stored model that may no longer run there.

**Why.** Status was a column nothing read; "deprecated" lived in two client maps and five routes.

**Rejected.** Sending `replacedBy` in the route's error body: the browser reads the replacement from its own catalog copy (1b-ii).

**Originated →** [2026-11-23-model-catalog-1b-server.md](../plans/2026-11-23-model-catalog-1b-server.md).

### D564 — Trigger tasks read the model from the catalog at run time *(recorded 2026-11-23; follows D561)*

**Decision.** The image, video and voice-preview tasks look the model's row up by id in the catalog when they run and dispatch through the adapter map with its `adapter_key`. They don't check the status again: the route did when it reserved the run. A missing row or adapter throws `ModelUnavailableError`; the image task aborts without a retry and its `onFailure` reports the failure, the video and voice-preview tasks report it from their catch, and each report refunds.

**Why.** Every payload already names the model; carrying the spec or key in the payload would add a contract between two separately deployed builds, and the voice preview payload names no model.

**Rejected.** The spec in the task payload (above). Re-checking the status in the task: a run already reserved keeps what it reserved with.

**Originated →** [2026-11-23-model-catalog-1b-server.md](../plans/2026-11-23-model-catalog-1b-server.md).
```
