# PRD — Posts in CreativeOS

**Date:** 2026-08-03
**Status:** Product decisions settled with the user 2026-08-03. Pending review.
**Owner:** Cyril Varghese
**Audience:** Product, design, engineering. This is the *what* and *why*. The *how* lives in the three
design specs linked in §11.

---

## 1. Summary

Designers generate images in CreativeOS, then leave for Canva to put copy on them. This PRD covers
bringing that step in: a **Post node** that composes text, shapes, images and icons over a generated
plate, gets a client's approval, and publishes.

> **Positioning:** **"They don't have to switch tools to generate on-brand images."**

That sentence is the product thesis and the scope rule. This editor does **not** compete with Canva
on editing quality — that race is unwinnable. It competes on not making you leave.

## 2. Context & problem

Image Gen produces a *plate*: a photographic background. What ships to a client is a **post** — that
plate with a headline, body copy, a CTA, a logo, and usually a colour band or price tag over it.

Today that final step happens outside the product, which costs four things:

1. **Brand identity is retyped.** Colours and fonts are looked up in a brand book and entered by hand into another tool, every time.
2. **The finished asset never returns.** It exists as a download, detached from the brief that produced it.
3. **Approval is untracked.** Clients approve over WhatsApp; nothing records what they saw or said.
4. **Compliance is unchecked.** Post copy is the only text in the pipeline a human writes by hand — every other text is model-generated under the brand's compliance constraints — and it is the text that publishes at full size on the client's own account.

## 3. Users

**Design agencies.** The tool is used by agency staff; the client is not a user of the editor.

| | Does | Wants |
|---|---|---|
| **Designer** (primary) | Composes posts; shares them for client approval. | Speed, and not looking up hex codes. |
| **Senior / Owner** | Reviews; publishes to live accounts. | Confidence nothing off-brand reaches a client's feed. |
| **Client** (external, no account) | Approves, or gives feedback. | To see exactly what will go out, without being asked to learn a tool. |

The client approves and comments — never composes. That single fact licenses a deliberately small
editor: a skilled designer with a constrained toolset and no tool-switching is well served, where a
brand-side marketer handed the same thing would find it missing features. We are building for the
first.

**Jobs to be done.** *Lay campaign copy over a ready plate without leaving CreativeOS. Apply the
brand's colours, fonts and icons without looking anything up. Have the caption written for me in the
brand's voice. Show the client exactly what publishes — artwork and caption — and get a yes or a
comment back.*

## 4. The scope rule

**Anything that only makes the *editor* better is out. Anything that makes the *pipeline* smarter is
in, at V1 or V2.**

This exists because the first feature request after launch will be a drop shadow, and the one after
that will be image filters, and each is individually reasonable. Canva wins that race; every hour
spent on it is an hour they already spent better. The wedge is everything either side of the
editing — the plate is already here, the brand is already here, approval and publishing are attached.

## 5. Release scope

| Area | **V1** | **V2** |
|---|---|---|
| **Editor** | Manual. Text, shapes, images, icons. Four templates. | Unchanged — it does not grow. |
| **Copy** | Caption + hashtags AI-generated one-shot; on-image text typed. | **All** text AI-generated, on the artwork. |
| **Image** | Copy-zone hint you read and paste into the image prompt. | **Layout-aware round trip** — pick a template, the plate regenerates to fit its copy zone. |
| **Formats** | One post node, one format. | Campaign fan-out — one composition re-fitted across formats. |
| **Language** | English + Tamil. | More Indian scripts; glyph-coverage checking. |
| **Compliance** | Warnings against the client's KB rules. | — |
| **Approval** | Shared link; approve or comment. | Pin-anchored comments; notifications. |
| **Publishing** | Instagram, Facebook, LinkedIn — staged behind platform approval. | Scheduling, carousels, video, per-network captions. |

**Explicitly never:** stock libraries, illustration packs, filters, effects, image manipulation,
blend modes, freeform drawing, text-on-curve.

## 6. Requirements

Tagged **[V1]** or **[V2]**. Requirements without a tag are V1.

### 6.1 Composition

| | Requirement | |
|---|---|---|
| R1.1 | A post is a node on the canvas that takes generated imagery as input and produces a rendered image as output. | V1 |
| R1.2 | Four layer kinds: **text**, **shape** (solid or gradient fill), **image**, **icon**. A gradient shape is how a scrim is made — light text over a busy plate is unreadable without one. | V1 |
| R1.3 | Layers can be added, deleted, reordered, locked, hidden, moved, resized and rotated directly on the canvas. | V1 |
| R1.4 | A layer list shows the stack, so a layer hidden behind another is still reachable. | V1 |
| R1.5 | Four format presets: Instagram square, Instagram story, LinkedIn, A4 print at 300 DPI. | V1 |
| R1.6 | Changing format after composing re-fits the layout and **warns** that a large ratio change will look wrong. No automatic re-layout. | V1 |
| R1.7 | One composition produces every format in a campaign, re-fitted. | V2 |
| R1.8 | Undo / redo. *Wins nobody over; its absence makes the tool feel cheap, which matters even when adoption is mandated.* | V1 |

### 6.2 Templates

| | Requirement | |
|---|---|---|
| R2.1 | Four starting compositions: **Lower third**, **Inset card**, **Side column**, **Split half** — named by composition, tagged by purpose (offer, launch, discount…). Composition is what decides whether a template fits the plate you have; purpose does not. | V1 |
| R2.2 | Templates are offered when a post is empty, and reachable afterwards from the header. They do not occupy permanent screen space — picking one is a once-per-post act. | V1 |
| R2.3 | Each template declares a **copy zone** — the region it will cover — surfaced as a copyable "image brief" sentence for the image prompt. | V1 |
| R2.4 | Picking a template regenerates the plate to fit its copy zone. *The thing Canva structurally cannot do, because it doesn't own the generator.* | V2 |
| R2.5 | Organisations can author their own templates. *Four hand-built compositions don't justify an authoring surface yet.* | V2 |

### 6.3 Brand

| | Requirement | |
|---|---|---|
| R3.1 | The brand's colours, fonts, logos, icons and evergreen hashtags come from the **client's KB** — never a parallel store, never retyped. | V1 |
| R3.2 | Where the KB lacks something, the panel says so and links straight to the KB to fix it. Absent, never silently empty. | V1 |
| R3.3 | Icons come from three sources: inbuilt pictograms, inbuilt brand marks, and the client's own uploads. | V1 |
| R3.4 | Client-licensed font files are **out of scope** — licensing plus font loading in an export renderer is its own problem. | — |

### 6.4 Copy

| | Requirement | |
|---|---|---|
| R4.1 | The **caption and hashtags live on the post**, not in the publish dialog — the client approves artwork and caption as one thing. An offer's terms, price and claims live in the caption. | V1 |
| R4.2 | Caption and hashtags are **AI-generated in one shot**, from the brand's tone, its compliance rules, its evergreen tags, the connected brief, and the rendered artwork itself. Editable by hand afterwards. | V1 |
| R4.3 | Generated copy is metered against credits like any other model call. | V1 |
| R4.4 | Regenerate, compare variants, and keep history. | V2 |
| R4.5 | On-image text (headline, body, CTA) is AI-generated. | V2 |
| R4.6 | Per-network captions and hashtag sets. | V2 |

### 6.5 Compliance

| | Requirement | |
|---|---|---|
| R5.1 | Post copy — on-image **and** caption **and** hashtags — is checked against the client's KB compliance rules: banned words, banned claims, tone, required disclaimers. | V1 |
| R5.2 | Compliance **warns and never blocks.** Not export, not publish, not even a banned word. *A tool designers are told to use, which also refuses to let them export, gets routed around. Warnings that are always right are worth more than a block that is occasionally wrong.* | V1 |
| R5.3 | A visible indicator shows the state at all times and lists each issue against the layer it came from. | V1 |
| R5.4 | Text contrast against what sits behind it is flagged advisory, with "add a scrim" as a one-click fix. Never a gate. | V1 |

### 6.6 Language

| | Requirement | |
|---|---|---|
| R6.1 | English and Tamil. | V1 |
| R6.2 | Every font offers a Tamil companion, and Tamil text falls back to it visibly. *A brand's Latin font has no Tamil glyphs at all.* | V1 |
| R6.3 | Warn when a font cannot render the text in a layer. **Accepted V1 risk:** a missing glyph renders as empty boxes in the preview *and* the export, and V1 will not catch it. | V2 |
| R6.4 | Malayalam, Kannada, Telugu, Bengali, Gurmukhi. | V2 |

### 6.7 Output

| | Requirement | |
|---|---|---|
| R7.1 | A post exports as an image that **matches the preview exactly**. | V1 |
| R7.2 | Export works at print resolution — A4 at 300 DPI. | V1 |
| R7.3 | The rendered post is available to the rest of the canvas like any other image. | V1 |
| R7.4 | Download always reflects the current composition, never a stale render. | V1 |

### 6.8 Approval

| | Requirement | |
|---|---|---|
| R8.1 | A client can review a post **without an account**, via a shared link. *No client-facing identity exists in the product, and building one is not justified for this.* | V1 |
| R8.2 | The client sees the artwork **and** the caption and hashtags — exactly what publishes. | V1 |
| R8.3 | The client can **approve or leave feedback**. Feedback is a comment thread. *"Make the headline bigger" is the normal response; a verdict-only system pushes that conversation back into WhatsApp, which is the thing being replaced.* | V1 |
| R8.4 | Approval applies to **that exact render**. Any subsequent edit invalidates it and requires another round. | V1 |
| R8.5 | Approval given offline can be recorded by a senior or owner, and is **labelled as recorded** wherever it appears — never presented as the client's own action. | V1 |
| R8.6 | Every approval round is retained. Nothing is overwritten. | V1 |
| R8.7 | Comments anchored to a point on the artwork; email notification on approval or comment. | V2 |

### 6.9 Publishing

| | Requirement | |
|---|---|---|
| R9.1 | Publish a post to a client's connected Instagram, Facebook Page, and LinkedIn organisation page. | V1 |
| R9.2 | **Nothing publishes without a current client approval** — including the manual hand-off. | V1 |
| R9.3 | The caption is **read-only** at publish. Editing it there would publish copy the client never saw. | V1 |
| R9.4 | Every publish is recorded: what image, what caption, which account, when, and the result. | V1 |
| R9.5 | A **"copy caption · download"** hand-off exists permanently, for expired tokens, unsupported networks, or posting by hand — and records the publication too. | V1 |
| R9.6 | Connection health is visible, and failures are stated in terms a human can act on. | V1 |
| R9.7 | Scheduling, carousels, video, Stories, first-comment hashtags, analytics. | V2 |

### 6.10 Permissions

| | Action | designer | senior | owner | client |
|---|---|---|---|---|---|
| R10.1 | Create, edit, render, download a post | ✅ | ✅ | ✅ | — |
| R10.2 | Share a post for client approval | ✅ | ✅ | ✅ | — |
| R10.3 | Approve · request changes | — | — | — | ✅ |
| R10.4 | Comment | ✅ | ✅ | ✅ | ✅ |
| R10.5 | Record an offline approval | ❌ | ✅ | ✅ | — |
| R10.6 | **Publish to a live account** | ❌ | ✅ | ✅ | — |

**One gate, not two.** Sending a post to a client is ordinary client contact and needs no internal
sign-off. The privileged act is **publishing to a live account**, which needs a senior or owner *and*
a current client approval.

## 7. Success criteria

| Signal | Why it matters |
|---|---|
| **Posts composed here rather than in Canva** | The thesis in one number. If designers keep leaving, nothing else matters. |
| **Time to create a post** | The direct measure of "didn't have to switch tools". |
| Round trips before client approval | Whether the approval loop actually got shorter. |
| Time from approved plate to approved post | End-to-end pipeline speed. |
| Compliance issues caught before publish | Whether the guardrail earns its place. |
| Brand-kit completeness per active client | Leading indicator — an empty brand kit makes the whole value proposition invisible on first use. |

**Kill signal:** if designers keep going to Canva, the answer is *not* more editor features. It means
the wedge is wrong.

## 8. Dependencies & external constraints

| | Impact |
|---|---|
| **Meta App Review + Business Verification** for Instagram and Facebook publishing — reported 2–6 weeks, multiple rounds likely, and only test accounts can connect until it clears. | **The critical path is a calendar, not code.** Submit on day one. Publishing is staged so nothing else waits on it. |
| **LinkedIn app verification** with organisational permissions. | Same; LinkedIn ships as its own stage when it clears. |
| **Client KBs must carry brand-kit data.** Existing KBs have none until re-extracted or filled by hand. | The Brand Kit degrades to empty states with fix-it links. Colours work immediately via existing data. Pick a pilot client whose KB is in good shape. |
| **A brand-icon library** is required — the installed icon set has no social marks and will never add them, on trademark grounds. | A new dependency, not optional, for any post with a contact strip. |

## 9. Risks

| Risk | Response |
|---|---|
| **Designers keep using Canva.** Outranks every technical risk. | The wedge is not editing quality (§4). Measured directly; if it misses, the answer is not more editor features. |
| The export doesn't match the preview. | Preview and export are the same renderer by design. Verified per format as a release gate. |
| Warn-only compliance lets a violation reach a client (R5.2). | Accepted deliberately. Visible at compose, render and publish, and the client sees the caption at approval. |
| Tamil renders as empty boxes and V1 doesn't catch it (R6.3). | Accepted deliberately. Font pairing makes it unlikely; manual check is a release gate; detection lands in V2. |
| A shared approval link is forwarded and the wrong person approves. | Accepted. It is the trust model of emailing a PDF, which is what it replaces — with expiry, revocation, per-post scope and a named approver on the record. |
| Platform approval slips past the pilot. | Publishing is staged; the assisted hand-off carries the pilot without it. |

## 10. Open questions

1. **Which pilot client goes first**, and is their KB complete enough to show brand-kit value on day one?
2. **Link expiry** is proposed at 30 days — long enough for a slow client, short enough to matter?
3. **Does a later "request changes" override an earlier approval** on the same render? Assumed yes.
4. **Should the client see previous rounds** and what changed between them? Assumed no in V1.
