Omni Multi-Shot Pipeline

Multishot is a property of one shot — not of a script, not of a model setting. The parse gains one number, the Shot node gains one flag, and two downstream nodes read it. Everything else already exists.

gemini-omni-1.1-flash 1 flag · 1 field 10s cap refs = File nodes $0.03–$0.30 / sec

01 · The pipeline

Where the new pieces sit

Parsing is unchanged apart from one added number. Grouping happens at fan-out, on the canvas, where you can see it and fix it.

Script Raw script text, pasted or uploaded source
→
Parse Unchanged, except each shot now returns a number v2 · duration_seconds
→
Fan out Packs consecutive shots up to 10s. Hybrid by construction. multishot: true | false
→
Motion prompt Reads the flag → ladder, or single-take prompt upstream check
→
Video gen Reads the flag → Omni-only picker, duration from the shot upstream check

A multishot shot goes straight to the motion prompt — no image-gen stage. There is no start frame to make: the generation is text_to_video from the shot's own description plus any connected File references. The image-gen path stays available and unchanged for shots that do want a still to animate (image_to_video). It is one option, not a required stage — which is the practical reason multishot is worth having: a cut sequence is described, not animated from a frame.

02 · D214

Hybrid fan-out, and the toggle

Five parsed shots totalling 22s. Fan-out walks them in order and closes a node before the next shot would break 10s — so the canvas comes out mixed, which is the point.

After fan-out 5 shots · 4+5+4+5+4s · 3 nodes
Shot 1–2 MULTISHOT · ON 9s
[0–4s]Hands lift the jar from a linen surface, morning light
[4–9s]Macro — the balm catches light as the lid turns
Shot 3 MULTISHOT · OFF 4s
singlePriya smooths it along her forearm, unhurried
Shot 4–5 MULTISHOT · ON 9s
[0–5s]She sets the jar down beside a cup of tea
[5–9s]Hero hold — label readable, CTA-safe negative space

22s in, 22s out. Shot 3 stands alone because adding it to the first node would make 13s, over the cap. Grouping is greedy and consecutive — it is not trying to find good seams. You see the result as nodes and fix it with the toggle, in the place the work already is.

What the toggle does
Node holdsToggleResult
N shots, on→ offSplits into N Shot nodes, order and lineage preserved, each single
1 shot, off→ onOne generation; the model may cut inside this single shot
1 shot, on→ offOne generation, one continuous take

Turning multishot off on a grouped node is a structural change — it creates nodes, so it confirms first and is undoable. There is no merge. To regroup, re-run fan-out. A merge has real unanswered questions (which half's edits win, what happens to downstream nodes wired to each) and is easy to add once the need is real.

Why the parse gains a number

duration today is free text copied out of the script — "22-26 seconds", "3 sec", "0-3s". Grouping to a 10s cap needs arithmetic, and deriving it from that prose at fan-out would fail silently on the formats it didn't anticipate. The model already reads the duration; it now also returns an integer. Missing or unparseable falls back to 4s, shown as assumed rather than parsed.

03 · D215

A reference is a File node

No cast, no script-level inputs, no new storage, no new UI. Connect a File node with the + that AddConnection already renders on the motion-prompt and video-gen focus views. The File node's title is the reference's name in the mention editor.

References attach downstream, not to the Shot. The video-gen route walks two levels — its own upstream plus the motion-prompt's. A File on the Shot node sits three levels away and would never be found. There is one motion-prompt per shot, so attaching there is shot-level in every way that matters, and needs no traversal change.

04 · D216

Two upstream checks

Motion prompt
Multishot A timecode ladder over the N shots, times from duration_seconds, summing to the node total.
Single Today's motion prompt, plus "In a single unbroken scene. No scene cuts."
Video gen
Multishot Picker shows only Gemini Omni, with the reason stated inline.
Single Every model, Omni included.
Duration Defaults to the shot total, clamped 3–10, editable, labelled with where it came from.
There is no continuous_take param

The Shot's toggle already carries that decision. A second control for the same thing is exactly the pair that drifts apart — and the draft this replaces had both. Filtering the picker rather than warning is the same instinct: pointing a timecode ladder at Veo returns one continuous take with the ladder silently ignored, which is indistinguishable from a bug after you've paid for it.

05 · D217

The docs are wrong about the request

Established by live probing against the real endpoint, for $0.09 total. Every schema fact below came free, using a trailing sentinel key the API can't know — if the error names the sentinel, everything before it was accepted.

The docs sayThe API says
video_config.durationUnknown parameter
video_config.resolutionUnknown parameter
duration is an integer 8Invalid input — it's the string "8s"
store:false for speedstore=true is required with delivery:"uri"
interaction.output_videoAbsent over REST — read steps[]

video_config accepts task and nothing else. Everything dimensional lives in response_format.

What actually works
{
  "model": "gemini-omni-1.1-flash",
  "input": [ /* image parts, then the text part */ ],
  "generation_config": { "video_config": { "task": "text_to_video" } },
  "response_format": {
    "type": "video",          // constant — never a param, never in the UI
    "resolution": "720p",
    "aspect_ratio": "16:9",
    "delivery": "uri",
    "duration": "8s"          // STRING, and it lives HERE
  },
  "store": true,              // forced by delivery:"uri"
  "background": false, "stream": false
}

A useful side effect of the forced store: true: storing the interaction is what makes previous_interaction_id editing possible — so the stateful edit chain is available later with no request-shape change. The superseded draft had claimed store: false forfeited it.

Three index bases, one renderer

Unchanged by the redesign, and still the thing that fails silently. The prompt-writing LLM emits mention tokens only; indices are assigned once, in code, per generation.

Omni's own declaration header carries two bases in one line: @ImageN counts the whole upload array from 1, while <IMAGE_REF_N> counts the references from 0. The provider always generates that header from the assigned roles — never simple inline tags, even when roles look unambiguous.

07 · Params

Which channel carries each control

All controls stay on the video-gen node, matching Veo and Kling. What differs is only how each one reaches the model — three are real API fields, three become sentences in the prompt.

Every param is in the primary group — the Advanced accordion was removed from the focus view in 7e1c643, so an advanced control renders nowhere. on_screen_text earns a control because Omni renders screen-space type correctly; a brand lock-up is still composited in post, since rendered-correctly is not typographically exact.

Kling multi_shot visible: false on both 3.0 and O1 — still sends its false default, renders nowhere. Hidden rather than deleted so the request shape is byte-identical, saved nodes keep resolving, and 3.0's end-frame rule that pins it stays valid.
continuous_take Gone. The Shot's multishot toggle is that decision.

08 · Cost

Why 360p changes the workflow

Hybrid fan-out already cuts the generation count — 22s becomes three requests instead of five. The draft tier cuts what each one costs by a further two thirds.

ResolutionPer secondThe 22s reel, 3 nodesNote
360p$0.03$0.66Draft tier — ~60% faster
720p$0.10$2.20Native, and the default
1080p$0.15$3.30Upscaled, not native
4k$0.30$6.60Upscaled, not native

Audio is always generated and always included in the rate, so Omni slots into the existing resolution-keyed pricing shape unchanged.
