Internal approval — flow reference

A prerequisite, then the seven steps of internal maker-checker approval, junior → senior → junior. Wireframe fidelity: the shapes and the state changes are the point, not the styling. Companion to the internal approval PRD — where the two disagree, the PRD is right and this file is stale.

Prerequisite — more than one user per organization

The flow below assumes an organization contains at least two people holding different roles. An organization with a single seat has no maker-checker separation to route or enforce, so none of the following exists until this does. Build it first.

Data flow at a glance

Two lanes, one loop. Purple marks the only two operations that write; everything else is derived on read, so there is no queue table, no assignment record, and no state to keep in sync.

Only two arrows write. Generating inserts a version row at pending; deciding updates that same row. Every count, drawer and popover in between is a read over approval_status — which is why there is no assignee column, no queue table, and nothing that can fall out of sync with the assets themselves.

R9.3–R9.4. The reviewer's note is read on the node, beside the controls that act on it. Regenerating writes a new version at pending, so the asset leaves the junior's list and returns to the senior's queue. Neither side resubmits anything.

The loop closes on one rule. A regenerate produces a new version at pending (D29). That single fact makes steps 7 → 2 automatic in both directions — no submit action, no resubmit action, and no assignee stored anywhere.
